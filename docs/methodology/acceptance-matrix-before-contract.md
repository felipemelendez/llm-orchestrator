# Acceptance matrix before contract

When adding a new gate, validator, or outcome contract to LLM Orchestrator, the **first artifact is the acceptance matrix, not the contract**. Each row of the matrix names a task shape and lists the expected behavior across every system component the new code touches: sniffer compel?, classifier verdict?, source class?, outcome label?, nudge family?, validator pass?. The matrix forces confrontation with shapes the first-principles design will miss. The discipline is: write the matrix, then check whether the contract you'd design from first principles can express every row cleanly. **If any row requires bolting on a state, the contract is incomplete — fix the contract, not the row.**

This rule exists because of one specific case. The research gate's outcome contract — `VERIFIED / COULDN'T_VERIFY / CONTRADICTED` — was designed from first principles ("what outcomes does verification produce?") and shipped through three step-3 rounds with smoke tests passing. Acceptance testing on a four-row matrix (Prisma design, openssl version lookup, Stripe vendor API, React CVE query) immediately exposed that two rows had no clean outcome: they were queries against project state, not verification of a planned approach. In emulation the agent literally wrote *"I had to bolt on a fourth state to be honest."* The fix was `NOT_APPLICABLE` — a fourth first-class outcome with required `Premise:` and `Reality:` fields. If the matrix had been the v0 artifact, that outcome would have been in the contract from day one instead of arriving four rework rounds later. The general lesson: **first-principles contract design defines its own coverage and can't see its own holes.** Acceptance cases define coverage from the outside and surface gaps automatically. For any future contract — a new validator outcome, a new dispatch routing decision, a new memory schema — the matrix comes first.

A second case proved the same rule. The orch-researcher's authority hierarchy — vendor MCP > Context7 > GitHub MCP > web search > training — was designed for the question shape "is this API current?" It worked cleanly for every row of the original four-row matrix, every CONTRADICTED catch (e.g., the Stripe webhook brief), and the smoke suite. A live trace on `/llm-orchestrator:cost` then dispatched the researcher against a task whose verification questions split half-and-half between SOURCES ("what's Anthropic's current pricing?") and LOCAL_STATE ("what does Claude Code's JSONL transcript schema actually look like?"). The agent answered both correctly but flagged `CONTRACT_FIT: awkward` in its own audit — the hierarchy didn't have a clean place for "the file on disk is the most authoritative thing here." The fix was a parallel `LOCAL_STATE` axis (filesystem `Read`/`Bash` > runtime inspection > filesystem MCP > training) that runs alongside the existing SOURCES axis, with per-question routing instead of one global tool order. The same lesson applies twice: a contract built around one epistemic kind (verify-against-upstream) cannot see questions of a different kind (inspect-local-state) until the matrix names them explicitly. **The first artifact is the acceptance matrix, not the contract — and the matrix must have rows that exercise every epistemic kind the system will encounter, not just the one the contract was designed around.**
