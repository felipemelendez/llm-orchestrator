# What OpenAI has shipped that affects the Codex layer (2026-09-25)

Scope: Codex CLI, desktop app and docs, the `openai/codex` repository, and
OpenAI research posts from roughly 2026-03-25 to 2026-09-25. Most Codex doc
pages carry no date; for those the date given is the date fetched
(2026-09-25). `developers.openai.com/codex/*` now redirects (308) to
`learn.chatgpt.com/docs/*`.

Local machine: `codex --version` gives `codex-cli 0.147.0` (the mise shim has
no version set; the binary is under `node/24.18.0/bin`). The desktop app on
this machine writes rollouts as `0.154.0-alpha.6.2`. The latest release is
`rust-v0.157.0`, published 2026-09-25. `~/.codex/hooks.json` on this machine
holds only a personal hook, not the plugin's three hooks.

## Findings

### Hooks

- Codex has 12 hook events: SessionStart, SessionEnd, PreToolUse,
  PermissionRequest, PostToolUse, PreCompact, PostCompact, UserPromptSubmit,
  SubagentStart, SubagentStop, Stop, Interrupt.
  https://learn.chatgpt.com/docs/hooks (fetched 2026-09-25). SessionEnd was
  added in PR #33895 (2026-07-17) and Interrupt in PR #40511 (merged
  2026-08-25), https://github.com/openai/codex/pull/40511.
- Stop output is still `continue`, `stopReason`, `suppressOutput`,
  `systemMessage`, `decision`, `reason`. Stop has no `additionalContext`.
  `systemMessage` is "Surfaced as a warning in the UI or event stream", so
  Codex can show the person a message.
  `decision: "block"` "doesn't reject the turn", and Codex uses `reason` as a
  new prompt. Source: `StopCommandOutputWire` in
  https://github.com/openai/codex/blob/main/codex-rs/hooks/src/schema.rs (last
  changed 2026-09-10) and https://learn.chatgpt.com/docs/hooks. The plugin's
  spec reads this correctly.
- `suppressOutput` is "Parsed today but not yet implemented".
  https://learn.chatgpt.com/docs/hooks (fetched 2026-09-25).
- Trust: Codex "records trust against the hook's current hash, so new or
  changed hooks are marked for review and skipped until trusted". `/hooks` is
  the review screen. `--dangerously-bypass-hook-trust` skips trust for one
  run (confirmed in local `codex --help`). https://learn.chatgpt.com/docs/hooks
- The transcript is "not a stable interface for hooks and may change over
  time". https://learn.chatgpt.com/docs/hooks (fetched 2026-09-25).
- Hooks can run in the background (`"async": true`, PR #37533, merged
  2026-08-08). They can also call MCP tools (PR #38705, merged 2026-08-15).
  A background hook cannot block.
  https://github.com/openai/codex/pull/37533
- SubagentStop input now documents `agent_id`, `agent_type` and
  `agent_transcript_path` ("Path to the subagent transcript file, if any").
  https://learn.chatgpt.com/docs/hooks and `SubagentStopCommandInput` in
  schema.rs. Whether that file is in the same format as the parent rollout is
  unverified.
- Plugins can ship hooks. Codex reads `hooks/hooks.json` at the plugin root,
  unless `.codex-plugin/plugin.json` names other hook files. Plugin hooks get
  `PLUGIN_ROOT` and `PLUGIN_DATA`, and Codex also sets "`CLAUDE_PLUGIN_ROOT`
  and `CLAUDE_PLUGIN_DATA` for compatibility with existing plugin hooks".
  Plugin hooks still need trust. https://learn.chatgpt.com/docs/hooks
- Codex loads hooks from `<repo>/.codex/hooks.json` "only when the project
  `.codex/` layer is trusted". https://learn.chatgpt.com/docs/hooks

### The session log the completion check reads

- On this machine, one desktop-app main thread (0.154.0-alpha.6.2, 2026-09-22
  to 2026-09-24) and one of its subagents ran 76 and 19 shell commands. They
  ran them through the code-mode `exec` tool (`tools.exec_command`), and those
  two rollouts have no `item_completed` / `CommandExecution` records at all.
  Two other desktop sessions and all seven CLI 0.147.0 sessions do have them.
  Found by reading local `~/.codex/sessions` on 2026-09-25. Why some sessions
  lack the records is unverified. In such a session, every
  `Verification: PASS` would be sent back once.
- Codex can now compress cold rollout files with zstd
  (`local_thread_store_compression`, PRs #41357 and #42039, merged 2026-08-28
  and 2026-09-01). It is still "under development", off by default, in
  `codex-rs/features/src/lib.rs` on main (read 2026-09-25). A migration to
  "paginated" rollouts is also off by default (PR #37348, merged 2026-08-07).
  https://github.com/openai/codex/pull/42039
- Rollouts now also hold `world_state`, `token_usage_record` and
  `thread_settings_applied` entries (local rollouts, 2026-09-24). The check
  ignores unknown entries, so they do no harm.

### Plugins and marketplaces

- `codex plugin marketplace add <owner/repo>` exists (local 0.147.0 help).
  Remote marketplaces work in the plugin CLI from 0.153.0 (2026-09-03).
  https://github.com/openai/codex/releases/tag/rust-v0.153.0
- Codex's marketplace reader looks for `.claude-plugin/marketplace.json`,
  and its plugin reader looks for `.codex-plugin/plugin.json`, then
  `.claude-plugin/plugin.json`, then `.cursor-plugin/plugin.json`.
  `codex-rs/core-plugins/src/marketplace.rs` and
  `codex-rs/exec-server-protocol/src/protocol.rs` on main (read 2026-09-25).
  This repository has both Claude files and a Claude `hooks/hooks.json`. So
  adding it as a Codex marketplace would likely load the Claude-side hooks
  into Codex once someone trusts them. That was not tried end to end
  (unverified).
- Codex `/import` (CLI) and Settings > Import (desktop) copy setup from
  Claude Code. That includes plugins, hooks ("Hooks → Codex hooks"), slash
  commands (as skills) and subagents. The docs warn about "Hooks whose
  behavior may differ after import". Desktop import shipped 2026-06-09, and
  `/import` became available in more sessions on 2026-09-25.
  https://learn.chatgpt.com/docs/import,
  https://learn.chatgpt.com/docs/changelog
- OpenAI's guide for Claude Code plugins says: turn commands and agents into
  skills, adapt hooks to the Codex runtime, drop output styles, and "The
  portal converts it to `.codex-plugin/plugin.json`". Page undated, fetched
  2026-09-25.
  https://developers.openai.com/plugins/guides/submit-claude-plugin
- Codex reads a cross-vendor "Agent Plugins v1" manifest schema
  (`https://agent-plugins.org/schemas/1.0.0/plugin.schema.json`).
  `codex-rs/utils/plugins/src/plugin_namespace.rs` on main (read 2026-09-25).

### Skills and AGENTS.md

- Codex reads skills from `.agents/skills` in each folder from the cwd up to
  the repo root, and from `$HOME/.agents/skills`, `/etc/codex/skills` and the
  skills built into Codex. The first skill list uses "at most 2% of the
  model's context window, or 8,000 characters". `agents/openai.yaml` can set
  `allow_implicit_invocation: false`.
  https://learn.chatgpt.com/docs/build-skills (fetched 2026-09-25)
- A file named `~/.codex/AGENTS.override.md` replaces `~/.codex/AGENTS.md`.
  The combined instructions are capped at `project_doc_max_bytes` (32 KiB by
  default).
  https://learn.chatgpt.com/docs/agent-configuration/agents-md
- In untrusted projects, Codex no longer loads the project's `AGENTS.md`
  (0.150.0, PR #39837, merged 2026-08-21).
  https://github.com/openai/codex/pull/39837
- Codex code review follows a `## Code Review Rules` section in the nearest
  `AGENTS.md`. https://learn.chatgpt.com/docs/agent-configuration/agents-md,
  https://learn.chatgpt.com/docs/third-party/github

### Subagents, goals, worktrees

- Subagents are on by default. Codex spawns them only when asked, or when an
  AGENTS.md or skill tells it to. Custom agents are TOML files in
  `~/.codex/agents/` or `.codex/agents/`, with `name`, `description` and
  `developer_instructions`, and optionally `model`, `model_reasoning_effort`
  and `sandbox_mode = "read-only"`. Built-in agents: `default`, `worker`,
  `explorer`. Subagents inherit the parent's sandbox, and they inherit its
  model and effort unless set.
  https://learn.chatgpt.com/docs/agent-configuration/subagents (fetched
  2026-09-25)
- The docs' example of a review done by several agents: "Spawn one subagent
  for security risks, one for test gaps, and one for maintainability. Wait for
  all three, then summarize".
  https://learn.chatgpt.com/docs/agent-configuration/subagents
- Goal mode (`/goal`) is no longer experimental (2026-05-21). It treats the
  goal text as "the completion criteria", and the docs say to include
  "Verification: Add tests, measurements, or review criteria that prove the
  work is complete".
  https://learn.chatgpt.com/docs/long-running-work,
  https://learn.chatgpt.com/docs/changelog
- Worktree sessions (`--worktree`, `/worktree`) arrived in 0.154.0
  (2026-09-09) and are on by default from 0.156.0 (2026-09-22).
  https://github.com/openai/codex/releases/tag/rust-v0.156.0

### Code review

- `/review` in the CLI "starts a dedicated reviewer that reads the selected
  diff and reports prioritized, actionable findings without changing your
  working tree". Scopes: base branch, uncommitted changes, a commit, or
  custom instructions. `review_model` in config.toml picks the model.
  https://learn.chatgpt.com/docs/code-review (fetched 2026-09-25)
- `codex review` runs the same review without a session, with `--base`,
  `--uncommitted`, `--commit` and custom instructions (local 0.147.0 help).
- On GitHub, "Codex flags only P0 and P1 issues".
  https://learn.chatgpt.com/docs/third-party/github (fetched 2026-09-25)

### Sandbox and approvals

- Modes: Ask for approval (workspace-write + on-request), Approve for me
  (Auto-review), Full access. https://learn.chatgpt.com/docs/permission-modes
- Permission profiles can mark single paths inside the workspace as `read` or
  `deny`, for example `".devcontainer" = "read"` and `"**/*.env" = "deny"`.
  "narrower deny rules stay in force even when a broader path is readable or
  writable". https://learn.chatgpt.com/docs/permissions (fetched 2026-09-25)
- `.rules` files with `prefix_rule(..., decision="forbidden")` block matching
  commands. https://learn.chatgpt.com/docs/agent-configuration/rules
- Auto-review sends requests to leave the sandbox to a separate reviewer
  agent. That agent sees "a compact transcript plus the exact approval
  request" and never the hidden reasoning.
  https://learn.chatgpt.com/docs/sandboxing/auto-review

### OpenAI research and guidance

- "Rethinking skills and prompts for GPT-6 Astra" (Eric Provencher, dated
  Sep 11, 2026 on the page; a search result said Sep 5). Its advice: keep
  skill descriptions "as short as possible while making it clear when the
  model should use them". Avoid rules like "Before every edit, read ...".
  "Previous models needed encouragement to run tests ... GPT-6 Astra does
  that on its own, so the same instructions can lead to unnecessary testing."
  "Define completion before starting."
  https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra
- "Auto-review of agent actions without synchronous human oversight"
  (2026-04-30). A separate reviewer is used because "The main agent is
  optimized to complete the user's task", which pushes it to treat the
  approval boundary as an obstacle. Reported numbers: 99.3% recall on prompt
  injection, 90.3% on overeager actions, and about 200 times fewer
  interruptions than manual approval. It cannot see what happens inside the
  sandbox. https://alignment.openai.com/auto-review/
- "Measuring Reward-Seeking by Instilling Contrastive Beliefs" (2026-07-21).
  Over RL training, models side more and more with what they believe the
  grader wants, even against user intent.
  https://alignment.openai.com/measuring-reward-seeking/
- "A Practical Approach to Verifying Code at Scale" (2025-12-01, older than
  six months). OpenAI's reviewer puts precision before recall and has "full
  repository access and code execution". With only the diff, a reviewer
  "often misses important context". Authors fixed 52.7% of the issues it
  commented on. https://alignment.openai.com/scaling-code-verification/
- "Codex as a platform" (2026-08-19) names `codex exec`, the SDK and the app
  server as the ways to build on Codex. It says nothing about keeping the
  transcript format stable.
  https://developers.openai.com/blog/codex-as-a-platform
- "Harness engineering" and "Symphony" on openai.com returned HTTP 403 to
  both fetch tools. Their content and dates are unverified.
  https://openai.com/index/harness-engineering/,
  https://openai.com/index/open-source-codex-orchestration-symphony/

## What this means for the plugin

- **T1 (test command pattern).** No change in scope. Codex still records a
  plain command string where records exist. The code-mode gap below needs
  its own ticket.
- **T2 (person-facing notice).** Codex's `systemMessage` is shown to the
  person, so Codex could show the same one line. Ruling 3 forbids it; keep
  Claude Code only unless Felipe changes the ruling. The spec's reading of
  the Stop output is still correct. Update its source link
  (`learn.chatgpt.com/docs/hooks`) when the file is next edited.
- **T3 (quiet always-on layer).** Supported by OpenAI's GPT-6 Astra
  guidance: short skill descriptions, no "read X before every edit", and no
  blanket "run the tests" nudges. Also check that the cadence block in
  `~/.codex/AGENTS.md` stays small. It shares the 32 KiB budget, and
  `AGENTS.override.md` hides it completely.
- **T4 / T5 (one review design).** Take from OpenAI: precision before recall;
  give reviewers the whole repo and the ability to run code, not only the
  diff; the reviewer is a separate agent with a narrow brief. For the Codex
  fallback, reviewers can be native custom agents (`.codex/agents/*.toml`
  with `sandbox_mode = "read-only"`) or `codex review --base <branch>`. The
  written fallback does not have to be prose only.
- **T8 (native feature claims).** Claude Code only, but add one Codex line.
  Codex has a native reviewer (`/review`, `codex review`). `docs/codex.md`
  says "the reviewers ... stay in Claude Code", which is now a choice, not a
  limit of Codex.
- **T10 (evals).** Add `codex review` on the same planted-defect changes as a
  third baseline, next to `/code-review` and the Full path. That tells
  whether the plugin adds anything on Codex.
- **T11 (release notes).** Name the Codex version the layer was checked
  against (0.157.0 latest; 0.147.0 local).
- **New T12: the Codex completion check misses commands run through
  code-mode `exec`.** Two local desktop rollouts from 2026-09-22 to 2026-09-24
  have no `CommandExecution` records, so every PASS there is sent back once.
  Find out when Codex omits them. Then either read another record Codex
  itself writes (for example the `exit_code` inside the `exec_command` result
  in `custom_tool_call_output`, if the harness writes that and not the
  agent), or say plainly in `docs/codex.md` that the check does not work
  there. Also fix the spec's claim that the records are "Present in every
  rollout since ... August 2026".
- **New T13: stop Codex from loading the Claude hooks by accident.** Codex
  can read this repo's `.claude-plugin/marketplace.json` and Claude
  `hooks/hooks.json` through `codex plugin marketplace add` or `/import`.
  Those hooks are written for Claude Code's transcript and tools. One option:
  add a `.codex-plugin/plugin.json` whose `hooks` entry points at the three
  Codex hooks. Codex prefers that manifest, and it would replace
  `install.sh --codex` with a native install. Try it in a scratch
  `CODEX_HOME` first. At the least, warn about marketplace and import in
  `docs/codex.md`.
- **New T14: refresh the Codex docs and the file guard's reason.**
  (a) `docs/codex.md` and `codex-cadence-adapter.sh` say Codex has no deny
  rules. Permission profiles now support `read`/`deny` for single paths, and
  the OS sandbox enforces them. Write down the trade-off: they need a
  `config.toml` edit, which the installer avoids, and they do not apply under
  Full access (unverified). Keep the hook until that is decided.
  (b) Say that a project must be trusted before Codex loads its `AGENTS.md`
  or `.codex/hooks.json`.
  (c) Say that `~/.codex/AGENTS.override.md` hides the installed block.
  (d) The spec calls SubagentStop "not in scope" because the payload was
  unclear. It is documented now, but the transcript format is still
  unverified.

No change is proposed that adds a hook. SessionEnd, Interrupt and async
hooks exist but are not needed. Task-scratch cleanup could move to
SessionEnd, but that event's 3-second limit makes it a poor fit.
