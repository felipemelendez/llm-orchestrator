# Tickets from the 2026-09-25 assessment

Each ticket is done by one agent with a fresh context window. The agent reads
this file, `2026-09-25-assessment.md`, `docs/llm-orchestrator/LAWS.md` and the
files its ticket names, and nothing is assumed from earlier conversations.

Research that informs the tickets is in `docs/llm-orchestrator/research/`:
`2026-09-25-anthropic.md`, `2026-09-25-openai.md` and
`2026-09-25-literature.md`. Read the sections a ticket points to. The
research files are leads, not proof: confirm a claim against the code, the
installed CLI or the docs before building on it.

These plan and research files are gitignored, so they exist only in
`~/src/llm-orchestrator/docs/llm-orchestrator/`, not in a ticket's worktree.
Read them from that path.

## Rules for every ticket

- Follow this repository's own laws (`docs/llm-orchestrator/LAWS.md`). The
  path named on each ticket is the minimum; raise it if the work turns out
  riskier.
- Work in the ticket's own worktree, on its branch (`refine/t<N>-<slug>`, cut
  from `refine/integration`). Commit there with one-line messages. Felipe
  authorized commits, branches and PRs for this refinement on 2026-09-25.
  Never push to, merge into or open work directly on `main`; only Felipe
  merges to `main`.
- Leave nothing unused behind. No project uses `workflow: legacy`, and nothing
  old is kept for compatibility: when a change makes code, tests, docs or
  config unused, delete them in the same ticket.
- Never edit `LAWS.md`, `cadence.json`, `LOCK.sha256`, `.claude/settings.json`
  or `.githooks/`. If the ticket needs one of them changed, stop and write the
  exact proposed change in the report; Felipe makes it under a numbered ruling.
- Add no new hooks. Change existing hooks only where the ticket says so.
- Never run paid evaluations (`tests/evals/`).
- Run the named checks as plain foreground commands and paste the result
  lines. End the report with
  `Verification: PASS | PENDING | BLOCKED | NOT APPLICABLE — reason`.
- Write in plain language. Update every doc that describes the changed
  behavior (README, `ARCHITECTURE.md`, skill text) in the same ticket.

## Review after each ticket

The controller (the main session) reads every diff and runs the checks again.
Fresh reviewers are added by path:

- Simple: the controller's review only.
- Standard: one fresh reviewer that did not see the implementer's report.
- Full: two fresh reviewers with different briefs (one against the ticket's
  "Done when" list, one plain-language adversarial) who never see each other's
  findings, and a refuter only if they disagree or one alone reports something
  serious.

## Branches and pull requests

- `refine/integration` is cut from `main`. Each ticket opens a PR from its
  branch into `refine/integration`. The controller merges a ticket PR only
  after its review passes and `bash tests/run-all.sh` passes on the merged
  result.
- When every ticket has landed, one PR from `refine/integration` into `main`
  goes to Felipe, who merges it.

## T1 — The completion check recognizes real test commands

**Path:** Full (touches two hubs: `scripts/lib/orch-completion-check.py` and
`scripts/hooks/orch-verify-gate.sh`). **Harness:** Claude Code and Codex.

**Problem.** The pattern in `scripts/lib/orch-signals.sh` (`ORCH_SIG_VERIFY_CMD`)
does not match `.ve/bin/pytest x`, `cd zapgram && .ve/bin/pytest x`,
`aws-vault exec --prompt=osascript testing-felipe -- .ve/bin/pytest x` or
`pnpm vitest run`. The check also ignores `runner.test_cmd` in the project's
`docs/llm-orchestrator/cadence.json`. A real passing run is then reported as
having no check behind it. The Codex check
(`scripts/lib/codex-completion-check.py`, `scripts/hooks/codex-verify-gate.sh`)
uses the same pattern.

**Change.**
1. Match a known runner after a path prefix (`.ve/bin/pytest`,
   `./node_modules/.bin/vitest`, `venv/bin/pytest`).
2. Match a known runner after a wrapper that ends its own options with `--`
   (`aws-vault exec … -- pytest`).
3. Match `pnpm vitest`, `pnpm jest`, `yarn vitest` and the same for `npx`.
4. When the project's `cadence.json` sets `runner.test_cmd`, count a command
   that starts with that text as a check, on both harnesses.
5. Keep today's rules: a failed, unfinished or backgrounded command does not
   count, and `|| true` stays out of scope as documented.

**Done when.**
- Each command above counts as a check in a new test case, on Claude Code and
  on Codex.
- A command that only prints (for example `echo pytest`) still does not count.
- `test_cmd` from `cadence.json` counts; a project without `cadence.json`
  behaves as before.
- `ARCHITECTURE.md` Layer 7 and `docs/specs/codex-completion-check.md`
  describe the new rules.

**Checks.** `bash tests/test-verify-gate.sh`,
`bash tests/test-codex-verify-gate.sh`, `bash tests/test-cadence-check.sh`,
`bash tests/test-hook-latency.sh`, then `bash tests/run-all.sh`.

**Stop if.** The pattern change makes `tests/test-hook-latency.sh` fail, or
matching `test_cmd` needs a JSON parser the hooks do not already use.

## T3 — Keep the always-on layer quiet for simple questions

process, and the headers compete with a project's own reply format.

   do not run them.

   choosing it drops Claude Code's own instructions on scoping and verifying

6. Cut always-loaded text: shorter skill and agent descriptions, no

   `claude plugin details llm-orchestrator` (about 3,067 tokens today, per

**Done when.**

## T4 — Spec: one review design for Standard and Full

**Path:** Full, spec stage only. No code. **Harness:** both.

**Problem.** `workflows/review-diff.js` (spec check, then quality check, then a
verification pass that executes proposed fixes) and the cadence Full path (two
blind reviewers, then a refuter only on disagreement) are separate designs.
`skills/cadence/CADENCE.md` says running the first does not count for the
second.

**Change.** Write a spec at
`docs/llm-orchestrator/specs/2026-09-25-one-review-design.md` that:
1. Names one design for Standard (one reviewer) and Full (two blind reviewers
   with different briefs, refuter only on disagreement or a one-sided serious
   or catastrophic finding). The field record in `docs/MEASUREMENTS.md`
   (the plain-language reviewer found 10 of 21 catastrophic defects alone)
   supports keeping the pair.
2. Keeps the parts of `review-diff.js` worth keeping: the JSON finding schema,
   counting every lost or malformed finding, the rule that a missing review is
   never a pass, and executing a proposed fix where the claim can be run.
3. Says what happens to `review-diff.js`, the `requesting-code-review` skill
   and `/llm-orchestrator:review`.
4. Describes the Workflow script for the Full path: inputs (spec, diff, harm
   ranking, briefs), each `agent()` call with its model named (LAWS section 3),
   the fixed rule that decides whether the refuter runs, and the return value.
5. Describes the written fallback for Codex and for sessions without the
   Workflow tool.
6. Lists what the script cannot do: ask the person mid-run, or run writing
   agents in a chosen worktree (`agent()` has no `cwd`). Fixing stays with the
   main agent.
7. Uses the research in `2026-09-25-literature.md` and `2026-09-25-openai.md`:
   - Every refuter verdict must cite evidence: a `file:line`, a test run, or
     the result of running the proposed fix. In one study, a checker held to
     this found 43 of 57 defects, against 34–36 for one or two plain reviewers.
   - The Full pair is one Claude reviewer and one GPT reviewer run through
     Codex, each on the most capable model its provider offers, named by
     alias or by the CLI's default so it stays current, and at a stated
     effort. One of the two keeps the plain-language adversarial brief; the
     spec says which and why. Every GPT finding on Claude-written code must
     pass the evidence rule above: one study found Codex reviewing Claude's
     code lowered the pass rate (91.4% to 82.8%) when reviewers could not run
     tests. Record the model each reviewer was actually served (LAWS
     section 3). If one provider is unavailable, the review is incomplete,
     never silently replaced.
   - Split diffs over about 150 lines; review quality falls sharply above that.
   - Give reviewers the repository and the ability to run code, not only the
     diff.
   - The adversarial brief checks for test tampering: deleted or skipped
     tests, weakened assertions, tests changed to match the code.
   - Record what happened to each finding (fixed, refuted, ignored) so the
     process can be measured over time.
   - On Codex, the fallback may use `codex review` and read-only custom agents
     (`.codex/agents/*.toml`) instead of written steps only.

**Done when.** The spec passes one fresh contract reviewer and one fresh
adversarial reviewer, and Felipe approves it.

**Checks.** None (spec only). `Verification: NOT APPLICABLE — spec only`.
